黑五虚拟礼品卡：系统级实施方案

礼品卡支付成功后直接生成卡号、系统 PIN、Code 128 条码并发送给收件人；无需激活或持有人绑定；发送礼品卡邮件前需验证客户邮箱，需要赠送时可转发已收到的邮件。POS 将礼品卡作为特殊商品加入购物车；礼品卡支付从购物车右上角“Benefits & Gift Card”入口完成在线验证、试算与预占。

核心设计结论

支付成功直接生成可使用的 ACTIVE 卡、系统 PIN、Code 128 条码。
购物车检测到礼品卡商品时，在 Checkout 按钮上方显示 T&C 勾选项；勾选后才启用 Checkout。支付成功后通过邮箱验证码确认收件地址，再发送礼品卡凭证。
礼品卡作为特殊 SKU 加入购物车，可与普通商品同单结算，但不参与税、积分和常规折扣。
旧礼品卡支付是购物车级 PaymentPlan，必须在订单预览前确定。
礼品卡售卡商品不能由旧礼品卡覆盖；其他支付至少覆盖新卡销售额。
拆分支付只拆 checkout 剩余金额；已预占礼品卡金额锁定，修改需重新试算。

代码现状与差距

三套代码已按线上分支同步后分析。现有购物车持续调用订单预览，创建订单直接消费预览快照；现有拆分支付则发生在订单创建之后，因此礼品卡支付计划需要前移，但剩余金额仍可复用原拆分框架。

关键差距

无自营卡账户没有余额、PIN、状态、扫码凭证和不可变流水。
支付确定过晚当前礼品卡在 checkout 后选择，无法影响预览中的膨胀权益。
无支付计划购物车变化后无法识别旧试算是否失效，也没有余额预占。
无门店销售配额活动只限定门店范围，不能控制每店可售数量。
首页无礼品卡入口需在现有两列 ShortcutCard 区增加统一礼品卡模块。
无凭证交付链路需要新增系统 PIN、Code 128 条码生成、邮件投递、重发与审计。

关键时序：checkout 前礼品卡支付计划

POS Cart → GiftCard API: verify(cardNo, PIN, cartSignature) GiftCard API → Order Preview: giftCardApplication(cardId, requestedPrincipal) Preview: 排除“新礼品卡销售行”，计算可用普通商品金额 Benefit Engine: 判断是否满足膨胀权益，生成行级 uplift 分摊 Payment Plan: CAS 预占本金与一次性权益，返回 planId / expiresAt POS: 展示固定礼品卡金额 + checkout 剩余金额 POS → Order Create: previewVersion + giftCardPlanId Order: 校验购物车签名与计划金额，创建订单 Split Payment: 仅对 remainingAmount 使用现金/银行卡等逐笔支付 全部覆盖成功 → commit plan；取消、超时或购物车变化 → release plan

业务流程、邮件交付与 checkout 前核销

购买支付前必须同意礼品卡 T&C；支付成功后生成卡号、系统 PIN 与 Code 128 条码，客户邮箱验证码通过后再发送礼品卡邮件。转赠等同于转发原邮件。旧礼品卡支付仍需在 checkout 前完成试算。

首页礼品卡模块加购→购物车识别礼品卡行→显示并勾选 T&C→启用原 Checkout 按钮→原 checkout 流程→支付成功生成卡号/PIN
填写客户邮箱→发送并验证验证码→发送卡号+PIN+Code 128 条码→需要赠送时直接转发邮件
验证码仅用于确认本次邮件收件地址，不建立持有人绑定，也不引入改绑或转赠状态机。卡号和 PIN 仍是使用凭证。
打开官网会员码扫描弹窗→扫描礼品卡 Code 128 条码→输入 PIN→验证并重新预览订单→继续原 checkout
查询原售卡交易→校验从未使用且余额完整→卡余额清零并作废→售卡实付按原支付方式退回
只看当前余额不够：必须同时满足 redeemed_count = 0、无核销流水、principal_balance = initial_principal。卡一经使用，即使后续商品退款令余额恢复到完整金额，也不再允许整卡退货。
已使用卡继续消费→0 < 本金余额 < $15→直接现金兑付并清零
已使用但余额仍 ≥ $15 时既不能退卡，也不能现金兑付；可继续正常消费，直至余额低于 $15。

卡状态机

PAID发卡 →ACTIVE_UNUSED未使用退货 →VOIDED_RETURN
ACTIVE_UNUSED首次核销 →ACTIVE_USED余额用尽 →DEPLETED
ACTIVE_USED余额低于 $15 并现金兑付 →CASHED_OUT
邮件转发不改变卡状态。ACTIVE_USED 是不可逆业务事实：后续商品退款可以增加卡余额，但不能恢复整卡退货资格。

checkout 前计算原则

礼品卡验证结果加入订单预览并重算膨胀权益、税和应付金额。购物车不显示 plan 横幅，也不新增 checkout 步骤；验证成功后直接回到现有 checkout 流程。

数据模型与接口

不做激活 claim 和持有人绑定；邮箱验证码仅保护礼品卡邮件投递。支付成功时生成卡号、系统 PIN 与 Code 128 条码载荷；收件邮箱只用于邮件交付，不代表账户所有权。

安全边界

卡号和 PIN 是 bearer credential。邮件可转发意味着任何获取完整凭证的人都能使用余额，因此必须对邮件内容、日志、导出、客服查询和重发权限进行严格控制。

礼品卡退货判定与事务

资格判定

returnable = status == ACTIVE_UNUSED AND redeemed_count == 0 AND principal_balance == initial_principal AND no_active_reservation AND original_sale_refundable
不能只用“当前余额等于完整余额”判断。任何历史核销都会永久取消整卡退货资格。

原子处理

锁定卡账户与原售卡交易，重新校验余额、状态和核销次数。
写入 CARD_RETURN_VOID 流水，将余额归零并把状态置为 VOIDED_RETURN。
按原售卡订单各支付方式的实际实付金额原路退款；售价与本金不相等时不得按本金超额退款。
退款失败则整笔回滚或进入可恢复补偿状态，禁止出现“钱已退、卡仍可用”。

并发与幂等

风险控制方式
退卡与核销同时发生退货与核销竞争同一账户 version；退货提交时再次验证 redeemed_count、完整余额与无预占
退卡成功但原路退款失败卡作废与退款指令使用 Saga / Outbox 补偿状态；退款完成前禁止恢复卡使用，支持幂等重试和人工告警
两台 POS 同时消费同一卡账户 version + available_balance 条件更新；计划、预占和流水同事务
购物车变化仍使用旧计划对商品、数量、折扣上下文生成 cart_signature；创建订单必须一致
支付只完成一部分计划保持 RESERVED；在剩余金额全覆盖后提交，取消/超时释放
门店配额超卖下单时 reserved_count 原子 +N；支付成功转 sold_count；取消/超时释放
重复发卡或重复发送销售单幂等键保证只发行一张卡；Outbox 与投递记录支持安全重试
支付回调重复(operation_type, idempotency_key) 唯一约束并返回首次结果
